# Successor candidates after CM-02 — v0.1

**Proposed, not run.** CM-02 closes the tested reference-representation comparison: W and an ordinary index have identical decisions, while exact retrieval is stronger for the addressed facts. Its small resident-object saving comes with other costs. Advance a new mechanism question; retain these strong controls.

## 1. Priority: learned task-progress state

**Identifier:** `NSS_TS01_LearnedTaskProgress_v0.1`, a new isolated feasibility study. Earlier conditional CM-03 cache/read-refresh proposals remain separate and unexecuted. Existing Q010 exports and frozen NSS role boundaries are unchanged. This is neither full NSS integration nor a low-bit learning experiment.

**Question and competing accounts.** Can a trained state transition maintain an evolving task ledger through interleaving, delay and revocation? A positive state-carry result would show a learned transition doing useful work beyond the latest reference. Alternatively, it may merely approximate an exact streaming algorithm at greater cost. A third possibility is a superficial recent-event shortcut that fails at switches or corrections. The experiment must distinguish these outcomes; it is not designed to assume neural superiority.

**Small task.** Two public task IDs each have an ordered four-milestone checklist. Public events are `COMPLETE(task, milestone)`, `REVOKE(task, milestone)`, `RESET(task)`, `ACTIVATE(task)` and unrelated distractors. Completion sets the named bit, revocation clears it, and reset clears that task's four bits. Other task bits remain unchanged. A query asks for the active task's four completion bits and first incomplete milestone, or DONE. The complete task state is therefore exactly representable by eight bits plus the active-task identifier; admit this cheap baseline explicitly. Labels are generated by a separate deterministic evaluator. Catalogue facts, if included, use identical exact lookup in every arm and are not the learned task target. This tests maintained, revised task progress, not just Q001-style retention of an early cue.

**Real learned mechanism.** Propose one small GRU transition `z_next = F(z_current, public_event)` with a fixed output head, at most 20,000 trainable parameters and one 64-float32 state per task (512 hidden-state bytes total). Only the event's addressed task is updated; activation selects the queried task. Queries read without rewriting. Weights are frozen during evaluation. No shadow completion-bit table is supplied to the learned arm. The exact event encoding, head, optimizer and loss must be frozen in Chat's protocol review; there is no hyperparameter sweep in this candidate.

**Required controls.** Compare carried learned state with (a) the same trained network reset before each event, explicitly an information-removal ablation; (b) the eight-bit exact streaming progress index, with its real implementation, metadata and update costs; and (c) full-prefix replay using the same trained transition, rebuilding each task from public history at every query. Replay and streaming controls receive exactly the same observed events and causal prefix. The replay control tests stored state versus repeated computation; it cannot access future events. Retain public exact retrieval for any factual subqueries. Charge replay scans, archive storage and all updates. Shared archive retention must be identical for total-memory comparisons; if the learned arm drops history, compare against an exact streaming arm allowed to drop it too.

**Data and budget proposal.** Train five seeds, each at most 2,000 optimizer updates with batch size 16 on new 17/33-event streams; no old Q010/CM evaluation data. Use three development and five held-out families, four 65-event sequences per family, and six query checkpoints (0/8/16/32/48/64): 32 sequences and 192 occasions total, comprising 72 development and 120 held-out occasions. Families vary event composition; templates cover delay/switch, interleaved progress, revocation/correction and reset. Five trained seeds repeat those same evaluation occasions, not create 600 independent held-out samples. Training, development and evaluation namespaces are `TS01/TRAIN-01..05`, `TS01/DEV-01..03` and `TS01/EVAL-01..05`; the exact deterministic seed derivation, stream templates and distractor balancing must be pinned before any training. Generate held-out content only after model/configuration choices are frozen. Development diagnostics do not authorize tuning on held-out outcomes.

**Predeclared proposed decisions.** Score exact checklist-plus-next-action correctness, per-task interference, wrong DONE and missed revocation separately, by family and trained seed. Require the streaming oracle to be correct on every generated case before admitting results. For feasibility, propose at least 95% aggregate held-out correctness in at least four of five trained seeds, positive carried-minus-reset differences in every family, and no undetected wrong DONE after an observed revocation. These are new design targets, not fitted CM-02 gates or population guarantees. Failure means the learned transition has not cleared this screen; preserve it without adjusting thresholds. Success establishes bounded learned-state competence only. Carry/replay parity with less total processing supports a recurrence/computation trade-off. An overall practical advantage requires a predeclared resource objective at matched correctness against the exact streaming index; if the index wins, report that and do not scale merely to seek a win.

**Full cost and stop rule.** Count all five fits and failed attempts, weights/checkpoints, optimizer state, event encoding, both task states, archive/index storage, prefix replay, verification and output. Proposed ceilings: 10,000 total optimizer updates, two hours shared wall time, 3 GiB sampled process-tree RSS and 2 GiB new output. These are stop ceilings, not host forecasts. Chat must estimate the exact transition/forward bound including prefix replay and fresh verification before freezing the protocol. Stop at a cap, leakage, source drift or oracle inconsistency; an incomplete run cannot meet the full five-seed criterion. Return raw held-out events/predictions, training curves, checkpoints, cost ledger, failures and independently computed scores. Reproduction requires a fresh computation, not reuse of output caches.

## 2. Conditional: explicit retrieval-time intent

CM-02 already demonstrates the pinned-versus-current distinction; repeating F:16 adds little. A new policy study is useful only for a mixed workload with explicit `AS_OF(revision)` versus `CURRENT_ENTITY` requests, corrections and deletion/re-creation boundaries. Compare deterministic pinned and revision-following policies under the same public request contract. Success is correct temporal selection and refusal of invalid revision chains, with all revision-index costs charged. This resolves product semantics, not cognition; defer until such a workload is wanted.

## 3. Conditional: public evidence of intent

No-cue wrong bindings cannot be repaired merely by remembering identical inputs longer. If intended identity is the next concern, add a declared observable cue (confirmation or correction), paired with absent/conflicting cue controls and exact cue-to-binding lookup. Score binding correctness separately from incidental content correctness and charge any clarification interaction. Keep hidden-intent labels out of producers. This tests the value and reliability of new information, not whether the model inferred an unknowable origin.

**Recommendation:** review TS01 first, with the exact-state control visible from the outset. The state/architecture/optimizer, exact seeds/templates, forward bound and feasible host limits remain freeze decisions; no study is execution-ready or authorized by this document. Learned recurrent-memory papers in `LITERATURE_NOTES.md` are mechanism precedents, not evidence that this candidate will outperform ordinary state management.
