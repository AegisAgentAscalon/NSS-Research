# Continuity handoff — HSA + segmented context, v1.0

## Current decision

**The component is PARKED FOR INTEGRATION after CAP02.** The user requested one bounded final preparation check, then a consolidated record so other theoretical ideas can proceed. Do not turn the open limitations below into automatic follow-up experiments. This handoff is not a study dispatch, serving-model adoption or authorization to run DARP.

The broader NSS direction has moved beyond tri-core as a required architecture. Stable weights during daytime use and candidate learning/repair during low usage is the preferred surrounding lifecycle; state and current evidence may still change during the day. This series does not qualify that complete lifecycle. The user accepts harmless drift while retaining identity, memories and abilities; these four-class fixtures do not measure companion identity.

## Objective

The investigation concerns HSA and segmented context as **NSS maintenance architecture**, including expanded usable information and capability as well as efficiency. Do not reframe it solely as attention-kernel speed. Tokens and JSON are intended to support explicit recording, handoffs and repair where useful. Approximately 25,000 language tokens is an untested budget idea; active-at-once and cumulative-night allowances were discussed separately, not fixed experimentally. DARP remains primarily an output architecture with maintenance outputs as one prospective application. [sources/context/RESEARCH_INTENT.md]

## What was built and tested

The fixed rule is DEFER on global freeze; otherwise COMPLETE if the task is complete; otherwise READY only when both supplied prerequisites are complete; otherwise BLOCKED. It is deliberately solvable exactly by ordinary code. The neural reader has 37 engineered features per record position, 18,500 parameters, width 32, two attention/FFN blocks and two heads. The HSA graph is task → region → global, with exact supplied prerequisites. Three levels are a retained design choice, not a measured optimum.

**SH01:** the first shared versioned-record/native-HSA prototype. Of four planned paired 600-update seeds, three pairs completed (8801/8802/8804). HSA confirmation was 6,133/6,144 versus dense 5,553/6,144 under the fixed recipe; the dense baseline was not exhaustively optimized. 8803/HSA remained interrupted with step-200 evidence; never use it as a completed fourth pair. Native sparse execution was slower. Source/packet caching reduced assembly but not reader traffic. [sources/SH01/REPORT.md]

**SH02:** separated topology, features, plans and execution, sharing K/V gathers among the four local queries. Retained weights/graph/answers; larger single-query batches improved over old HSA but the smallest shape became slower and dense often stayed faster. Historical bitwise replay failed even in unchanged code, while declared numerical tolerance and classes passed; retain that unresolved historical distinction. [sources/SH02/REPORT.md]

**SC01:** exact backward-closure segments with jobs, revisions, receipts and JSON resume. Strong conventional caching was supplied the same information, result reuse and progress facilities. All 324 executions preserved full-reference behavior. Most saving came from ordinary reuse; custom grouping sometimes added calls or latency. Every single task still required global task-query metadata. Oversized closures explicitly deferred. [sources/SC01/REPORT.md]

**SC02:** incremental publication, vector compilation, reusable graph plans and exact-signature reuse improved some workloads. On contemporaneous 32-task churn, old SC01 took 20.939 ms and improved scheduled execution 16.367 ms. Do not subtract historical 24.195 ms from current 12.939 ms: unchanged SC01 itself ran at 13.144 ms in that later session. The intermediate neural cache avoided about 47% of first-layer row work but was slower in all 20 timing cells; leave it optional/off by default. Generic cache baselines also benefited from the engineering changes. All 720 main executions preserved behavior. [sources/SC02/REPORT.md]

**CAP01:** carries running softmax maximum, denominator and weighted numerator over key tiles; uses external exact source/embedding/layer arrays. It preserves one joint attention calculation and original graph, not separately normalized partial answers. All 488 cases completed with 32 active query+key record positions in the primary grid. Calculations needing 69–755 original input positions per selected HSA task completed without truncation. Ordinary streaming obtained the same capacity and decisions as custom grouping. Of 3,904 decisions none changed from full same-weight references; numerical envelopes passed. Changed-source checkpoints were rejected and restarted, not selectively migrated. Residual larger-layout learned errors also occurred in the full reference. [sources/CAP01/REPORT.md]

**CAP02:** one final preparation/retention test from the six exact dense/HSA parents, U untouched; S 96 extra eight-task updates; M 96 updates cycling 8/32/128 tasks. Main 1,152 updates plus three disposable preflight updates; no random refits. Fresh HSA M selected accuracy: eight tasks 768/768, 32 tasks 767/768, 128 tasks 766/768, separate 512 stress 189/192. Whole eight-answer jobs: 96/96, 95/96, 94/96 and 21/24. HSA small-task retention was complete on this panel. M repaired the 19 original 128-task errors but introduced two others, including one false COMPLETE. Three false READY answers remained at 512. Equal labels/updates were not equal source information or FLOPs; training was resident, not constrained to the 32-record tile. Twelve post-learning streaming checks passed, not streamed evaluation of every new world. [sources/CAP02/REPORT.md]

## Conclusions that are supported

A working bounded component exists. HSA's supplied structural bias helped this rule. Source-bound segmented job execution and exact multi-pass attention increase executable input reach. A modest broader preparation phase can improve the learner's use of larger layouts without losing the tested small rule. These are meaningful outcomes even though not every proposed optimization helps or every output is correct.

Custom hierarchical grouping is not uniquely necessary: ordinary multi-pass execution matches its answer capability. Smaller attention/input counts are not total memory or energy savings. Record positions are not language tokens. Evidence access is not novel procedural understanding, and a valid JSON envelope is not a language model writing a complete maintenance handoff.

## Integration boundary

Later work still needs actual tokenized maintenance inputs/outputs, source-grounded semantic selection, summary completeness, task reconstruction from explicit notes, realistic archive and total-memory costs, and the full learning/repair/adoption lifecycle. The preserved functions are useful foundations, not proof those gaps have been solved. DARP's maintenance-output concept was the next discussed candidate, but do not start it without a specific user request.
