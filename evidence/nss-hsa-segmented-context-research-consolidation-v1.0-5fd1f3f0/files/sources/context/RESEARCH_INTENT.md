# Current research intent and scope record

**Source:** the owner's statements and clarifications in the current NSS research conversation, ending with the consolidation request on 28 September 2026. This is an editorial record of that conversation, not a verbatim exported transcript or a prospective study protocol. It does not authorize a new experiment.

## Explicit owner statements

> “I thought we were moving past the tri-core design?”

NSS is the research project, not a requirement to preserve a Primary/Secondary/Tertiary arrangement. Historical topology proposals and prior results remain historical references.

> “Yeah, I think it's probably better to stick with our cold during the day, learns and repairs during the night idea.”

The preferred surrounding lifecycle keeps serving weights stable during use and learns/repairs a candidate during low usage. The discussion distinguishes fixed serving weights from evolving task state and current source-backed evidence. None of SH01–CAP02 qualifies that full lifecycle.

> “Yeah, I also think we should utilize tokens for maintenance tasks where possible.”

Tokens and explicit records are tools for maintenance and continuity, not something to eliminate because recurrent state is also being investigated. JSON was discussed as a candidate common explicit message format; there was no serialization/tokenizer efficiency comparison.

> “25,000, I imagine, is likely sufficient if we utilize tokens efficient”

The 25,000-token scale is an owner hypothesis, not a measured limit. Active-at-once context and cumulative maintenance traffic were distinguished during discussion, without a fixed language-token experiment being adopted. The older concept's million-token examples are not current measured requirements.

> “And DARP is largely intended as an output architecture too”

DARP's primary role is output generation/refinement, not context management. Applying it to maintenance outputs is a candidate next-component use. DARP was not implemented or run in the six archived studies.

> “Remember, the core goal is testing the efficiency of these ideas as maintenance architecture for the NSS.”

Component work serves NSS recording, evidence use, consolidation/repair support and task handoff. It is not an invitation to silently replace the research objective with generic model benchmarks.

> “To be fair, we do have to make sure we have a working architecture concept for these ideas before we really throw them into the ring. So building and testing one-by-one is probably not a bad idea.”

Functional component design, implementation and diagnosis are legitimate prerequisites. A working implementation is distinct from an efficiency advantage; component interactions may also matter.

> “I also really want to see if segmented context and HSA work because then we could talk about combining them into one architecture.”

The initial shared versioned interface and separate dense/HSA and management paths directly addressed this interest.

> “So three is probably good.”

The owner preferred keeping the current three-level hierarchy rather than adding depth unnecessarily. No hierarchy-depth optimization experiment established that three is optimal.

> “Some drift is okay, as long as the core identity, memories, and abilities are retained.”

Harmless numerical or expressive variation is not a product defect by definition. Stored evidence integrity, behavioral retention and actual identity continuity remain separate requirements; the present classifier does not test companion identity.

> “I do wonder, my core intention with segmented context + HSA wasn't about speed but about expanded capability.”

CAP01 redirected the evaluation toward capacity beyond resident input limits. CAP02 followed with one bounded larger-layout preparation/retention check. Speed remains a resource consideration, not the sole purpose.

> “Okay, we can do that. But if we've demonstrated that this at least works, let's not longer too much longer here.”

The final preparation pass was intended to be bounded. CAP02 parks the component for integration rather than creating an automatic sequence of further optimization studies.

## Current request and output boundary

The user requested a consolidated document/archive of the HSA/segmented-context research, including questions, tests, results and conclusions, especially for maintenance-token architecture, before moving to other theoretical ideas. The present package contains SH01, SH02, SC01, SC02, CAP01 and CAP02 original executions and a source-grounded synthesis. It adds no model training, inference, new test outcomes, DARP execution or serving-model adoption.
