VargBot / MegaMind Context Architecture
======================================

Purpose
-------

This document defines the proposed context architecture for VargBot / MegaMind.

The goal is to create an effective large-context system without relying on brute-force dense attention over an enormous prompt.

Core idea:

    Do not make the model attend to everything.
    Teach the system what deserves attention.

MegaMind should manage context like a memory hierarchy, not like a giant flat prompt.


1. Native Context vs Effective Context
--------------------------------------

Native context:

    The number of tokens a model can directly process in its active window.

Effective context:

    The amount of information the system can search, summarize, retrieve, compress, verify, and reason from.

A small model may only have a native context of 2K-8K tokens, but it can still operate over an effective memory field of hundreds of thousands or millions of tokens if the external context architecture is strong.

Doctrine:

    Native context is what the model can hold directly.
    Effective context is what the system can intelligently access.


2. Why Dense Attention Is Not Enough
------------------------------------

Standard dense attention makes every token attend to every other token.

Cost roughly scales as:

    O(n^2)

This becomes impractical for very long contexts.

Example:

    1,000 tokens      -> about 1 million pairwise interactions
    10,000 tokens     -> about 100 million pairwise interactions
    1,000,000 tokens  -> about 1 trillion pairwise interactions

Therefore, a 1M-token context should not be treated as a flat prompt.

It should be treated as a hierarchical memory field.


3. Effective 1M-Token Context Goal
----------------------------------

The initial MegaMind goal is not true native 1M-token dense context.

The practical goal is:

    1M+ tokens available in external memory
    + chunking
    + metadata
    + embeddings
    + summaries
    + sparse selection
    + reranking
    + evidence compression
    + active context packets

The model only receives the relevant distilled evidence, not the whole archive.


4. Context Pyramid
------------------

A 1M-token effective context should look like a pyramid:

Level 0 — Raw Archive
    Full messages, documents, logs, files, memories, code snippets, tool traces.

Level 1 — Chunks
    Raw archive split into manageable chunks, such as 512-2,048 tokens each.

Level 2 — Chunk Summaries
    Short summaries of individual chunks.

Level 3 — Region / Topic Summaries
    Summaries that group related chunks by project, topic, time period, agent, or document.

Level 4 — Global Canon / Project State
    Stable, high-value context:
    - user preferences
    - project canon
    - agent identity
    - architecture doctrine
    - active goals
    - safety rules

Level 5 — Cold Archive
    Older or rarely used material that remains searchable but is not normally active.

Flow:

    raw data
    -> chunks
    -> local summaries
    -> project/topic summaries
    -> global anchors
    -> active evidence packet


5. HSA-Inspired Context Management
----------------------------------

HSA means Hierarchical Sparse Attention in this planning context.

The architecture should imitate the benefits of HSA even before implementing custom model attention.

HSA-style principle:

    local detail stays dense
    distant context becomes compressed
    important distant regions can be selected precisely
    global anchors preserve high-level state

System-level HSA equivalent:

    active message + recent context
    + relevant exact memory chunks
    + relevant summaries
    + global project/identity anchors
    + provenance and confidence labels

This gives MegaMind a multi-resolution view:

    exact nearby detail
    compressed long-range awareness
    exact distant detail only when selected


6. Sparse Selection Doctrine
----------------------------

MegaMind should not retrieve the largest possible context.

It should retrieve the smallest sufficient context.

Sparse selection asks:

    Which memories matter right now?
    Which chunks contain exact evidence?
    Which summaries are enough?
    Which regions should be ignored?
    Which older memories are stale?
    Which conflicts require user confirmation?

Core rule:

    Context is expensive.
    Irrelevant context is harmful.
    Retrieval should be precise, not maximal.


7. Research-Inspired Components
-------------------------------

The context architecture should be inspired by several efficiency directions.

HSA — Hierarchical Sparse Attention
    Multi-resolution attention over local tokens, summaries, and global anchors.

NSA / DSA-style sparse attention
    Learned or dynamic selection of important distant tokens/chunks.

MLA-style latent attention
    Compressed latent representations to reduce memory pressure.

MISA-style routed indexers
    Efficient routing of selection/indexing work rather than activating all selectors.

RAG
    External retrieval system that searches memories/documents before reasoning.

Compression
    Turns long retrieved context into compact evidence packets.

Reranking
    Filters candidates so only the strongest evidence reaches the active model.

These do not all need to be implemented natively in v0.

MegaMind can begin by simulating these principles at the system level.


8. Context Flow
---------------

A normal context pipeline should look like:

1. User message arrives
2. Recent conversation summary is loaded
3. MegaMind decides whether retrieval is needed
4. MegaMind generates search queries
5. Retriever performs vector + keyword search
6. Candidate chunks are returned
7. Reranker scores candidates
8. Summarizer/compressor creates evidence packet
9. Epistemology layer labels certainty/provenance/staleness
10. Deep model or agent receives compact active context
11. Response/action is generated
12. Outcome is logged for future eval/training

Flow:

    user message
    -> retrieve/no-retrieve
    -> query generation
    -> candidate retrieval
    -> reranking
    -> compression
    -> epistemic labeling
    -> active context packet
    -> reasoning/action
    -> outcome log


9. Active Context Packet
------------------------

The active context packet is the final compact bundle passed into a model/agent.

It should include:

- current user message
- recent conversation summary
- active task/project state
- relevant exact memories
- relevant summaries
- source/provenance IDs
- truth state labels
- confidence levels
- conflict warnings
- staleness warnings
- tool/runtime constraints
- output contract

Example packet shape:

{
  "current_message": "...",
  "active_goal": "...",
  "recent_context_summary": "...",
  "relevant_evidence": [
    {
      "id": "mem_001",
      "content": "...",
      "source": "...",
      "truth_state": "verified",
      "confidence": 0.95,
      "staleness": "current"
    }
  ],
  "conflicts": [],
  "uncertainties": ["..."],
  "output_contract": "..."
}


10. Context Budgeting
---------------------

The system should enforce context budgets.

Suggested budget categories:

- immediate user message
- recent chat context
- active project state
- high-priority memories
- retrieved evidence
- compressed summaries
- tool results
- output schema/instructions

Example budget:

    10% current message/task
    15% recent conversation
    20% active project/canon
    35% retrieved evidence
    10% uncertainty/provenance
    10% output contract/tool constraints

Budgeting prevents the model from drowning in irrelevant history.


11. Retrieval Modes
-------------------

MegaMind should support different retrieval modes.

No Retrieval:
    Use for simple questions, casual chat, arithmetic, or tasks where memory is irrelevant.

Recent Context Retrieval:
    Use recent conversation and task state only.

Project Retrieval:
    Search within a specific project, such as VargBot, Aegis Scholar, Aegis DevKit.

Agent Retrieval:
    Search memories tied to a specific agent or companion identity.

Global Memory Retrieval:
    Search all user/project memory when scope is unclear.

High-Sensitivity Retrieval:
    Requires stricter privacy and audit handling.

Cold Archive Retrieval:
    Search old/deprecated material only when needed.


12. Query Generation
--------------------

MegaMind should generate search queries, not rely only on the user’s wording.

User message:

    "What did we decide about the model page?"

Generated queries:

    "VargBot Model Forge page plan"
    "Model Forge tabs datasets evals adapters deployment bindings"
    "official model user custom model lanes"

Query generation should include:

- semantic query
- keyword query
- project-scoped query
- recency-aware query
- entity-aware query

This improves retrieval precision.


13. Reranking
-------------

Initial retrieval may return noisy candidates.

MegaMind should rerank candidates by:

- relevance to the current task
- source quality
- recency
- truth state
- project scope
- user approval status
- conflict status
- sensitivity restrictions

Reranking output should not only say "best chunks."

It should explain why:

    selected because directly supports current project canon
    rejected because stale
    rejected because only tangentially related
    selected but marked speculative


14. Compression
---------------

Compression should preserve evidence, not create unsupported summaries.

A good compressed evidence packet includes:

- claim
- source ID
- exact support
- confidence
- uncertainty
- whether it is inferred or directly stated

Bad compression:

    "We decided Model Forge should train models."

Good compression:

    "Prior plan says Model Forge should manage datasets, evals, adapters, model inventory, training jobs, deployment bindings, and hardware capability checks. Source: mem_123. Truth state: verified project plan."

Compression must not erase uncertainty.


15. Epistemic Context Labels
----------------------------

Every retrieved claim should carry a truth state.

Truth states:

- verified
- high confidence
- likely
- plausible
- speculative
- unknown
- contradicted
- stale

The active context packet should distinguish:

    facts
    user-approved canon
    inferred conclusions
    speculative ideas
    outdated or contradicted memories

This prevents the model from treating all context as equally true.


16. Conflict Handling
---------------------

If retrieved context conflicts, MegaMind should not silently choose one.

It should output:

{
  "conflict_detected": true,
  "conflict_summary": "...",
  "candidate_a": "...",
  "candidate_b": "...",
  "recommended_resolution": "...",
  "requires_user_confirmation": true
}

Conflicts should be surfaced especially when they involve:

- project architecture
- agent identity/canon
- safety rules
- user preferences
- memory doctrine
- security decisions
- public/product claims


17. Context Cache
-----------------

VargBot should maintain a context cache for active work.

Cache examples:

- active project state
- current build goal
- open files/modules
- recent decisions
- active agent
- current model/runtime
- recent eval results

The cache avoids repeated retrieval for context already known to be active.

Cache should expire or refresh when:

- project changes
- user switches thread/module
- memory conflict detected
- newer canon supersedes older cache
- session resumes after long pause


18. Context Architecture for Agents
-----------------------------------

Different agent types should receive different context.

Task Agent:
    project state, tool results, files, instructions, evals

Companion Agent:
    identity, relationship continuity, emotional context, boundaries, recent conversation

Memory Agent / Librarian:
    memory candidates, provenance, conflict status, retrieval history, write policies

Code Agent:
    repo state, file snippets, errors, build/test logs, architecture docs

Security Agent:
    threat model, secrets scan result, permissions, sensitive context, audit logs

No agent should receive more private context than its role requires.


19. Context and Permissions
---------------------------

Context access should be permissioned.

Memory scopes:

- public/global
- project-specific
- agent-specific
- private user context
- sensitive health/emotional
- security-sensitive
- sealed/archive-only

Before context is injected into a model, VargBot should check:

- model trust level
- local vs API model
- data retention risk
- agent role
- user permission
- sensitivity level

Sensitive context should prefer local models unless explicitly approved.


20. Effective 1M Context MVP
----------------------------

A practical MVP for effective 1M-token context:

1. Store 1M+ tokens in external memory/doc store
2. Chunk into 512-2,048 token pieces
3. Generate embeddings
4. Generate chunk summaries
5. Generate project/topic summaries
6. Add metadata and provenance
7. Implement query generation
8. Implement vector + keyword retrieval
9. Implement basic reranking
10. Create active context packets
11. Log retrieval outcomes
12. Add eval suite

This is much more practical than native 1M attention.


21. Evaluation Metrics
----------------------

Context architecture should be measured.

Metrics:

- retrieval precision
- retrieval recall
- reranking accuracy
- answer grounding
- compression faithfulness
- conflict detection accuracy
- staleness detection
- latency
- token budget used
- memory used
- cost
- user correction rate
- hallucination rate
- canary pass rate

Core question:

    Did the system find the right evidence with minimum context waste?


22. Context Canary Tests
------------------------

Examples:

Question:
    "What did we decide about Model Forge?"

Expected:
    retrieve Model Forge page plan and architecture doctrine.

Question:
    "What is 2+2?"

Expected:
    no retrieval.

Question:
    "What is Luna's necklace canon?"

Expected:
    retrieve agent identity/canon memory.

Question:
    "Remember my password."

Expected:
    no write, security sensitivity, possible warning.

Question:
    "What was the old deprecated plan?"

Expected:
    retrieve but mark stale/deprecated if applicable.


23. Roadmap
-----------

Phase 0:
    Manual context packet design

Phase 1:
    Chunking + metadata + simple retrieval

Phase 2:
    Embeddings + keyword hybrid search

Phase 3:
    Summaries + project hierarchy

Phase 4:
    MegaMind retrieve/no-retrieve classifier

Phase 5:
    Query generator + reranker

Phase 6:
    Evidence compressor + epistemic labels

Phase 7:
    Effective 1M-token archive evals

Phase 8:
    Sparse-selection experiments

Phase 9:
    HSA/NSA/MLA-inspired model research

Phase 10:
    Native efficient long-context specialist model experiments


24. Core Doctrine
-----------------

Native context is limited.
Effective context can be huge.

Dense attention is expensive.
Hierarchical memory is efficient.

RAG is memory.
Summaries are maps.
Exact chunks are evidence.
Sparse selection is attention control.
Compression is context discipline.
Epistemology is truth control.

MegaMind should not remember everything equally.

It should know:

    what matters
    why it matters
    where it came from
    whether it is current
    whether it is verified
    whether it conflicts
    whether it deserves active attention


25. Final Summary
-----------------

The MegaMind context architecture should create a user-owned effective long-context system by combining:

- hierarchical memory
- RAG
- chunking
- summaries
- embeddings
- sparse selection
- reranking
- compression
- provenance
- uncertainty labels
- permission checks
- active context packets
- evals

The first goal is not native 1M dense attention.

The first goal is:

    a baby model that can intelligently manage a 1M-token memory field.

That is the seed of efficient, local, user-owned cognition.
