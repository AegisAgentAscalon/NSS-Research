Version 0.1 | Proposed identifier DIRECT01

**Status:** planning candidate only; not an execution dispatch. Optional follow-up to the current evidence-led roadmap. No model, hardware, tokenizer, source revision, thresholds, or execution budget has been selected.

## Recommendation

Keep the practical route in the current plan: COMP01 establishes a competent language-capable reference, then MEM01 and PREP01 test useful memory and preparation before CYCLE01 asks whether learning accumulates. ADAPT01 remains one conditional, single-mechanism investigation. This is a decision sequence, not a seven-stage prerequisite waterfall: if cost blocks a stage, measure and address the blocker; a bounded mechanistic study can proceed when it answers a clear question, but it does not qualify the companion.

The roadmap is strongest where it separates current evidence from weight learning, gives ordinary retrieval/replay strong controls, tests accumulated accepted revisions rather than reset-to-parent corrections, and treats a fallible evaluator as something to measure. Keep resource measurement and a small end-to-end smoke test throughout; BUDGET01 should optimize an observed bottleneck, not postpone feasibility checks. Preserve FCR-0103-001 after NBR-03 and before NBR-04, and the named RET-MW01-FIT-001 return, without turning either into an obligation to perfect every historical prototype. The roadmap is ready for COMP01 protocol preparation, not model selection or execution by implication.

**Evidence reconciliation:** the new plan reports RECOVER01 v0.2 results (152,606 post-learning errors reduced to 1,055, 32 corrected class mappings retained, residual false-DONE and numerical failure) and cites BALANCE01, TRACE01 and later charter/foundation records. This workspace review found the old RECOVER01 proposal but not those named newer source files. Treat the newer findings as plan-reported, preserve their limitations, and obtain exact source identities in Chat before using them as a dispatch input. Do not mark the old proposal as execution evidence, erase failed gates, or rerun completed studies merely to repair documentation. The same distinction applies to the report-derived DARP results below.

“Direct generation from weights” is best made precise as an output-interface hypothesis. Both ordinary autoregressive (AR) and parallel systems apply weights to input-dependent activations; weights are not a store of prompt-addressable finished answers. Given a shared representation `h`, AR predicts ordered fields as `p(y_j | h, y_<j)`, while a simple parallel head predicts `p(y_j | h)` for all fields together. A shared slot processor could coordinate fields, but a factorized head does not represent every possible dependency among them. It must still learn from data, use the right evidence, respect order and task state, and pass the same checks.

Treat DIRECT01 as an optional small structured-output probe after COMP01 competence and when output generation presents a live quality/cost bottleneck or a distinct bounded capability hypothesis. The default path is a language-capable COMP01 baseline followed, if useful, by a MEM01/PREP01 output probe. A retained four-field toy fixture is an alternate *mechanism-only* route when it isolates the question cheaply; it is not an extra mandatory run and cannot substitute for companion competence or prove free-form language ability. Do not restore an obsolete core topology or make diffusion/DARP the assumed solution.

## Evidence motivating the question

The DARP03 report says its supported four-step denoising writer was close to, but not practically better than, its similarly supported AR reference: static complete handoffs were 359/384 versus 361/384; changed-plan handoffs tied at 128/150; common erroneous blocks repaired were 391/431 versus 386/431; sampled median episode time was 10.041 versus 9.418 ms; and false-COMPLETE candidate outputs were 6 versus 1. The supplied exact checker blocked invalid commits; candidate errors were not successful external actions. These are reported historical measurements, not measurements repeated for this proposal. [local source: `sources/NSS_DARP_Research_Results_Analysis_and_Decision_v1.0.docx`, sections 13–18; extracted text in `sources/DARP_TEXT.txt`]

That result parks the tested DARP implementation; it neither disproves parallel output generally nor establishes equivalence. The fixture’s wrapper supplied 13 of 17 tokens, leaving four substantive fields for four denoising steps. That leaves limited parallel work to amortize and is a plausible concern, not an isolated causal finding. Its tiny closed rule, three inherited parent pairs, perfect task-specific localization/checking, small CPU timing sample, and unoptimized full-prefix AR path limit generalization. The workflow (draft, check, edit, bind evidence, commit) remains reusable with AR. [Source: supplied DARP consolidation sections 3–5 and 16–18; architectural interpretation is this handoff’s hypothesis.]

The next question is narrower: on a shared, competent context representation and identical structured task, can a jointly predicted output block meet the AR readout’s quality at a better measured full cost, or improve quality at an acceptable added cost? Existing AR weights cannot be assumed to work with an unfamiliar parallel readout without training and evaluation. This should not become DARP04, an architecture replacement, or a claim of plug-in compatibility.

## Smallest useful comparison to preregister

The default entry is after COMP01 has shown that the selected language-capable trunk can use gold evidence and perform the task family. Record inadequate task families as trunk limitations. Preserve informative comparisons on prospectively eligible competent families; do not impose an error-free baseline gate. If no usable family remains, stop as a feasibility limitation rather than a decoder verdict. If COMP01 is not yet feasible, Chat can prepare a fixture-only plan, explicitly labeled mechanistic and conditional.

For the primary mechanism test, freeze one competent trunk and input/evidence representation. Train **both** a new conventional AR readout and a new direct parallel structured readout on the same approved examples, targets, task-state fields and evidence. This compares output interfaces while controlling the representation; it is not a practical replacement test against a mature, fully tuned writer. Disclose differences in readout parameters, optimization, training tokens, target exposure, FLOPs and measured tuning cost rather than hiding them behind equal step counts. A later practical replacement comparison, if warranted, would give each complete writer the same bounded tuning budget; do not add it as another arm now.

Both readouts must emit the same ordered field/value inventory through the same exact serializer and outer wrapper. Do not compare parallel field classifiers against an AR system that must also learn JSON punctuation. If fields are atomic labels, call the AR comparator a semantic-field decoder, not native unrestricted next-token generation. If using text spans, freeze tokenizer, boundary and parsing rules. The wrapper must not reveal learned field values or answers. AR may use a normal incremental KV cache; do not handicap it with a naive full-prefix implementation. Report AR’s causal conditioning on earlier generated fields and the parallel head’s lack of that conditioning as intrinsic to the tested interface. Standard teacher-forced training is allowed, with generated-prefix mismatch evaluated and reported.

Neither arm receives repair or checker feedback in the primary comparison: the checker only scores or rejects its initial candidate. Parallel output uses one readout pass after the common trunk encoding; record encoding and decoding work separately. For multi-block handoffs, both arms consume their own earlier outputs under the same predeclared rejection/continuation policy; never silently replace a failed block with gold context. A single bounded check/repair pass may be tested only as a separately labeled secondary comparison on the same fixed drafts, with its training/inference and checking costs charged separately. Do not conceal repair as part of a “one-pass” result. Keep model/evidence/task/prefix/tokenizer changes explicit: any cached context representation must be invalidated when its source, model, task state, prefix or tokenizer changes.

Use a small set of deterministic structured families that require field coordination: independent fields; order/action changes; a field that changes completion status; and continuation where a later block depends on the accepted prior block. Use an exact-rule ceiling to separate representation/readout errors from task/evidence ambiguity. Development and confirmation must be split by underlying histories or task families, not random output tokens. Pair arms on identical histories; report underlying histories as task units, inherited trunks as clusters and readout seeds as nested replicates; shared-backbone readouts are not independent pretrained models. Reserve confirmation untouched by tuning.

Score raw candidate outputs, semantic field correctness, whole-record/whole-handoff validity, cross-field/order consistency, false completion, and downstream exact-checker acceptance separately. Report invalid candidate drafts even if the checker blocks them; checker rejection is safe containment, not correct generation. For language tasks, the exact structural checker is not a semantic oracle: use a source-grounded independent rubric and adjudicated sample, or mark that family unresolved. “Exact-rule ceiling” applies only where the task rule and target are genuinely known.

## Outcomes, costs and stopping

Predeclare `ΔQ = Q_parallel − Q_AR` on primary whole-handoff outcomes and `R_C = full_cost_parallel / full_cost_AR`, alongside each parent/seed and critical-error category. Define `C` as one declared measurable quantity, such as end-to-end serving time at fixed hardware/batch/concurrency; report other resources separately rather than adding bytes and milliseconds. If preparation/training is amortized, predeclare the serving horizon `n` and use `T_prep + T_train + n*T_serve`; show unamortized costs too. During bounded development, determine whether the fixture and instrumentation are feasible and set any numerical decision bands prospectively; freeze them before confirmation. Do not borrow DARP03’s gates or invent a latency target before the model/device exists. A decision can be “quality win,” “cost win within predeclared quality/critical-error bounds,” “tradeoff,” “no useful difference,” “mechanism failure,” or “technical stop.” Do not pool away a parent regression or let easy field accuracy offset false completion or broken continuation.

Measure full cost: parameter count and checkpoint bytes; training targets/tokens and compute; per-phase wall time; cold and warm inference; actual input/output tokens; peak and retained RAM/VRAM; cache memory/lifetime; checking/repair; and complete task latency. Report both amortized training and per-query serving where relevant. Keep every valid parent and failure. Stop for resource/integrity faults or invalid evaluators; a scientific miss is still reported. A new quality/cost winner is local to this task and working point, not companion qualification.

Before any future run, freeze the exact model and source/license, tokenizer, device/runtime, readout equations/interface, parameter and training-budget accounting, eligible data and target construction, splits/seeds, wrapper/serializer, state/prefix protocol, checker/rubric, numerical decision rules, resource caps, cache invalidation, manifests and failure/stop handling. Unknown model downloads require explicit authorization; this planning note authorizes none.
